Reading a result

The screen cannot tell you whether a test passed. A rule that never fired produces a perfectly clean save — identical to a rule that fired and approved the order. Check the log after every single case.

Real pass

Invoke + Return Success

Two rows for asi_Order_Validator_t2, no Validation row. The rule ran and allowed the save.

Real block

Validation row present

A Validation row carries the message and the v2err# code. Compare the code to the Expected column.

Void — not a pass

No rows at all

The rule did not fire. Scoping, pool cache, or status. The case proves nothing; fix and re-run before recording anything.

A fourth outcome worth naming: an Error row, or a RuleError mentioning "rule-binding problem, not an order problem", means the registration drifted again — almost certainly because the rule was opened and saved in Rule Manager. Stop testing and re-run verify-required-elements.sql; every result after that point is suspect.

Other rules share this screen, and two of them muddy the evidence.

ribbon_oe_default_branch and _ribbon_pro_perks both return Fail with "Ship To ID is required." on any order lacking a ship-to. They fire on load, seconds before the validator fires on save. That message looks like a validation block and is not one — check which rule owns the log row before attributing it. EncodeFileToBase64 fails on every single invocation and has done since 2018; ignore it.

asi_oe_suppress_oe_msgs hooks P21 message-box events and can set suppress_message='Y' to hide one. It matches on message_no against a four-row table (5 ALLOW, 451/688/8280 SUPPRESS), and a validator block is a business-rule return message rather than a numbered P21 message, so it should be out of scope. If a Validation row ever appears in the log with no popup on screen, that rule is the first suspect. Note it also emails an alert for any message number it does not recognise, and BRR has live SMTP.

04

Cost measurement

Script: Measure-Validator-Cost.sql. Logical reads and CPU from the plan-cache DMVs plus DataSet payload bytes — never wall-clock, which on these servers has reported the opposite of the truth.

The payload numbers already in the log are not a baseline. The kb_Order_Validator_v2 samples of ~52,972 bytes were captured on 2026-09-01 while kb_ was itself on the damaged 74/3 registration. They measure kb_ crippled. Against _t2's 54,055 they would "prove" the rewrite made things worse. kb_ is now repaired to 114/11 and has to be re-measured from scratch.

  1. Snapshot the plan cache (STEP 1).
  2. kb_ → 704, _t2 → 705 by SQL. Recycle pools. Save the test order.
  3. Capture with @phase='kb'.
  4. Snapshot again. Flip back: _t2 → 704, kb_ → 705. Recycle pools.
  5. Save the same order. Capture with @phase='t2'.
  6. Report (STEP 3).

Expect _t2 to move fewer DataSet bytes — it asks for 76 fields across 5 DataWindows against kb_'s 114 across 11. Expect it to issue more SQL statements: five small native SELECTs replacing one TVF call. Both are true at once, and the round-trip count is a real cost that should be reported alongside the reads, not buried under them. If the rewrite is not faster, that is a legitimate result — the case for it is retiring nine kb_ objects and the custom stored procedure dependency, not speed.

G6v2err#0 Blank credit status · blank carrier · blank packing basis The three numeric precursor guards look unreachable — see below

The numeric precursor guards may be dead code. Order 6043906 has a genuinely blank ship-to. The DataSet delivered ship_to_id as decimal(0) with an empty value — and the rule returned Success, with no block, no exception and no error row. Dec() nulls only on row.IsNull(), so a DataWindow numeric that arrives blank rather than DBNull never trips !HasValue.

That likely makes all three numeric guards — freight_code_uid, ship_to_id, customer_id — unreachable in practice. This is not a port regression: kb_ used Field<decimal?>().HasValue on the same DataRow and would behave identically. It is pre-existing, and it means P21's own field validation is the only thing actually stopping a blank ship-to. Worth confirming against kb_ during the paired cost run, while both rules can still be switched.

06

What none of this proves

Branch coverage shows every decision path fires and returns the right code. It is not an equivalence proof. The two rules could agree on all eleven cases above and still diverge on the long tail — the corpus re-save against the 2026-09-01 kb_ baseline, diffed both directions, remains the test that settles that.

Two known divergences are deliberate and will show up in that diff. The validator reads customer.credit_status directly while the note writer reads the corporate rollup; they disagree for 577 customers. And four [PRESERVED-BUG] behaviours were carried over intact — an unrecognised carrier still bypasses checks 1, 3, 4 and 6 entirely. Neither is a port defect; both are business decisions still open.
