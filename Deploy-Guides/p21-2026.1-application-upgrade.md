## 2. Hard prerequisites — **IT department owns these**

The middleware installer bootstrapper and `sql32.exe` are .NET **Framework** apps. They will not run until the box is prepared. This gate has now blocked us twice (25.2 and 2026.1).

### 2.1 .NET Framework 4.8 (the current blocker)

Check on every middleware / scheduler box that will run Setup:

```powershell
(Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full' -ErrorAction SilentlyContinue).Release
# >= 528040  -> 4.8 present
# missing key / lower value -> NOT installed  (this is our error)
```

Fix (IT):
- **Windows Server 2019 / 2022:** Server Manager → *Add Roles and Features* → *Features* → **.NET Framework 4.8** + **ASP.NET 4.8**, and **.NET Framework 3.5**.
- **Windows Server 2016:** 4.8 is **not** in Add Features — run the offline installer `ndp48-x86-x64-allos-enu.exe`.
- **Reboot.** The installer error persists while a reboot is pending even after 4.8 is in.
- Do **not** work around it by 7-Zip-extracting the installer ("expand files") — the middleware genuinely needs the 4.8 runtime.

### 2.2 Server roles & features (KB0137871 pp.4–5 / KB0086487)

Full IIS role set under Web Server (IIS): Common HTTP Features, Health & Diagnostics (all), Performance (Static + Dynamic Content), Security (Basic / Windows / Digest / Client Cert Mapping / IIS Client Cert Mapping / URL Auth / Request Filtering), Application Development (**.NET Extensibility 3.5 + 4.8**, **ASP.NET 3.5 + 4.8**, ASP, CGI, IAPI Extensions, SSI, Application Initialization), Management Tools (Console, Scripts & Tools, Management Service).
Features: **.NET 3.5**, **.NET 4.8 + ASP.NET 4.8**, WCF Services (MSMQ Activation, Named Pipe, TCP Activation, TCP Port Sharing).

### 2.3 Other IT items

- **TLS 1.0 and 1.1 must be present on the middleware server for the WebUI** (KB0086487). Confirm before disabling legacy TLS.
- **Scheduler needs the `IIS-ApplicationInit` feature** (2025.2 RG) — installer auto-enables, may force a reboot.
- **`.NET 10` / ASP.NET Core Hosting Bundle** — 2026.1 migrates middleware components to .NET 10. Exact hosting-bundle requirement is in the **2026.1 Middleware Installation Guide on EpicWeb** (the copy in the OneDrive folder is 2023 and obsolete — download the current one).
- **Crystal Reports Runtime 13.0.34** (64-bit; 32-bit too if present) — handled by the Middleware Readiness Utility (§6), needs **up to two reboots**, machine-wide, off-hours.
- **OS:** 2026.1 wants Windows Server **2019 or 2022**. If any P21 middleware box is Server 2016, plan an OS refresh.
- **SQL Server:** 2026.1 tested on SQL 2022; minimum SQL 2016 **with DB compatibility level ≥ 130**. Recommend landing the DB on **SQL 2019/2022** as part of this project so 2026.2 doesn't force a second migration.
- **Hardware:** re-check against *Prophet 21 Hardware Requirements* (middleware ≈ 4 vCPU / 48 GB per ≤75 users; highest available clock speed matters most).

## 5. Upgrade runbook

### Phase 0 — Prep (no installer yet)

1. IT completes **§2** on the `P21Upgrade` middleware box; re-run the middleware Setup to confirm the .NET gate is cleared.
2. Download from EpicWeb → *Prophet 21 → Downloads → Current Release*: `Epicor.P21.Middleware.Install.2026.1.x`, `SQL_2026.1.x`, current **Middleware Installation Guide**, custom Crystal Forms if upgrading them.
3. Open an Epicor case: confirm the **2021.1 → 2026.1** path (single `sql32` pass vs. required interim stop) and expected conversion runtime against a Prod-sized DB (§9).
4. Run the **§3.1 BR Assembly-Name audit** (Appendix B) — long pole, start now.
5. Capture the **§4** API baseline from Prod.
6. `C:\P21Installs\2026.1.x\` on the middleware box; sub-folders `SQL` and `SCRIPTS`. Never install from a network path or the OneDrive folder.

### Phase 1 — Rebuild the P21Upgrade env

7. Back up the current 25.2 `P21Upgrade` DB (throwaway, cheap insurance).
8. **Restore last night's Prod (2021.1) backup** into `P21Upgrade`.
9. Set DB **compatibility level ≥ 130**.
10. Remove the **Web Apps** component per **§3.6** (registry export first).

### Phase 2 — Upgrade, **timed** (record wall-clock per step; the `sql32` step is the Prod outage estimate)

11. IIS: stop the P21 SOA site + all its application pools (batch file `Stop_Specific_App_Pools.zip` attached to KB0137871).
12. Run `Epicor.P21.Middleware.Install.2026.1.x` **as Administrator** → select the instance → drive → Install.
13. Extract `SQL_2026.1.x` into `C:\P21Installs\2026.1.x\SQL`. Run `…\Middleware\P21Upgrade\Accessories\sql32\sql32.exe` → connect via a DB profile → **File → Update database…** → point at the SQL folder → read the confirmation, verify the DB name, **Yes**. **Run the DB update once per version only.**
14. Re-run the middleware installer if the wizard didn't open; then open **Middleware Configuration as Administrator**.
15. Walk the wizard using the **§4.1 baseline values** (Appendix A page list). Watch: External Server Name (from the old Web Apps URL), certificate selection (My Store, personal cert matching the FQDN — not WebHosting), Port Bindings, Scheduler Location URL, Business Rules path, filehandler UNC paths (must be UNC; identical across all instances on one DB).
16. Run the **Prophet 21 Middleware Readiness Utility** when prompted (§6).
17. Click the **red X** on the Setup Complete page (required, or the app pools won't start). Start the site + pools.

### Phase 3 — Functional validation

Run **§7**. Sign off per area.

### Phase 4 — Absorb the delta

18. Diff post-upgrade `web.config` / `appsettings.json` / Middleware Config against the §4 baseline — shows exactly what 2026.1 rewrote about API/auth.
19. Run `SQL-Schema\SqlSchemaCompareProd2Upg.scmp` (Prod → upgraded `P21Upgrade`) to enumerate the schema delta our customizations must absorb at Prod cutover.

### Phase 5 — Repeat on Play, then plan Prod

20. Repeat Phases 1–4 on **P21Play** (and BRR for the WWMS/BR path). Only then schedule the Prod cutover with a costed outage window from the Phase 2 timings.

## 6. Middleware Readiness Utility (Crystal runtime) — KB0136386 / KB0135833 / *About the Middleware Readiness Utility*

- Runs automatically every time Middleware Configuration runs; can also be run standalone (`p21-middleware-readiness-win.exe`, or `C:\Program Files\Prophet 21 Middleware Readiness\` → Run as Administrator).
- Checks/updates: **.NET Framework version**, **Crystal Reports Runtime** (target **13.0.34**, 64-bit required, 32-bit updated if present), fonts, barcode libraries.
- Machine-wide; affects **all P21 instances on the box**; **up to two restarts**; auto-relaunches after login. **Run off-hours.**
- Auto-stops the `Epicor Prophet 21 SOA - formsandreporting` app pools; restart them after if you stopped them manually.
- Log: `C:\Epicor\Prophet21\Middleware\P21Upgrade\logs\*.html` → *Provider: Crystal Reports Runtime version analysis provider* → confirm **Required = Current = 13.0.34** for both 32- and 64-bit. If mismatched: uninstall the wrong Crystal Runtime via Programs & Features, re-run the utility, restart.
- Don't **Skip** steps — later analysis depends on earlier ones. **Exit** is resumable.

## 8. Rollback

P21 DB conversion is **one-way** — there is no downgrade.

- **P21Upgrade / Play dry runs:** rollback = re-restore the source DB from the Prod backup and reinstall the prior middleware build. Cheap; expected to be used iteratively.
- **Prod cutover:** rollback = restore the pre-cutover DB backup + reinstall the 21.1.4559.345 middleware + restore the Web Apps site from the pre-removal registry export and installer. Decision point and max rollback time to be set from the Phase 2 timings; document in the Prod cutover plan before scheduling. **Keep the current 21.1.4559.345 middleware + Web Apps installers archived** — they may not stay downloadable from EpicWeb once 2026.1 ships.
- Keep the pre-cutover backup and the API §4 baseline for at least 30 days post-go-live.

## Appendix B — BR Assembly-Name collision audit (§3.1)

Run per environment, against every Business Rules share (`\\ASP21FS1\<env>\...\BusinessRules\` and the BRR path). Groups with more than one file **or** more than one `AssemblyName` under one file name are the problem set.

```powershell
# Point at each env's Business Rules folder
$brPath = '\\ASP21FS1\Play\BusinessRules'   # repeat per env

Get-ChildItem $brPath -Filter *.dll -Recurse | ForEach-Object {
    $f = $_
    try {
        $an = [System.Reflection.AssemblyName]::GetAssemblyName($f.FullName).Name
    } catch { $an = "<<unreadable: $($_.Exception.Message)>>" }
    [pscustomobject]@{
        Folder       = $f.DirectoryName
        FileName     = $f.Name
        AssemblyName = $an
        Version      = (try { [System.Diagnostics.FileVersionInfo]::GetVersionInfo($f.FullName).FileVersion } catch { $null })
        Modified     = $f.LastWriteTime
    }
} | Tee-Object -Variable rows | Sort-Object AssemblyName, FileName | Format-Table -Auto

"`n=== COLLISIONS (same AssemblyName, >1 file) ==="
$rows | Group-Object AssemblyName | Where-Object Count -gt 1 |
    ForEach-Object { $_.Group | Select-Object AssemblyName, FileName, Version, Folder, Modified } |
    Format-Table -Auto
```

Then for each collision: keep the current DLL, remove obsolete copies (EpicCare ticket to Cloud Ops if a DLL is locked), or — for genuinely distinct rules — edit `AssemblyName` in the project, rebuild, redeploy. Cross-check against `business_rule` / `business_rule_data_element` and the `kb-replacement-tracker.csv` so this doubles as kb_ retirement work. Feed results into [[businessrulesdll-share-cleanup.md]].
