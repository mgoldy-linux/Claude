## What the query does
Mirrors `BR SAL WILL ADVISE`'s open-order logic (not complete/deleted/cancelled at the line,
not deleted/RMA/quote at the header, no child lines), with:
- **Carrier = Will Call** → `p21_view_oe_hdr.carrier_id = 10002` (plain WHERE equality).
  Traced via `bi_view_carrier`'s definition (`[Carrier ID]`/`[Carrier Name]` off
  `p21_view_address` where `carrier_flag='Y'`) — P21 stores carriers as address records, there
  is no separate `carrier` name table. Confirmed id 10002 identical in Play and Prod; re-verify
  if this portal is ever cloned to a new environment.
- **Branch restriction** → `asi_fnt_get_user_loc('<user_id>')` (a P21 runtime token, substituted
  server-side per logged-in user). Originally built against `kb_fnt_get_user_loc`; swapped to
  `asi_fnt_get_user_loc` — see KB retirement section below.
- **Columns dropped:** Cost (`commission_cost`), the duplicate Unit column, Extended Cost
  (`extended_cost`), and the footer's `sum(extended_cost)` total.
- **Column added:** Promise Date (`p21_view_oe_hdr.promise_date`).
- **Sort:** `ORDER BY order_date DESC` (source portal was `ASC`).

## KB retirement — zero kb_ dependencies
Originally reused `kb_fnt_get_user_loc('<user_id>')` unchanged from the source portal (flagged
per standing policy, not fixed, since it's a large actively-maintained function with real
per-user exceptions — out of scope to rewrite for a single portal). At the user's request,
swapped to `asi_fnt_get_user_loc`, which **turned out to already exist** as a proven
2026-04-14 rebuild in both Play and Prod (drops `kb_view_users` entirely, rebuilt off
`p21_view_users`/`p21_view_roles`/`users_ud`, same live exception logic — DASHLEY, Ops Region
matching, 100/101, 140/143, 142/144, 281/221). Verified equivalence with `EXCEPT` both
directions for a real multi-region test user (`island2`) before swapping — 0 rows either
direction, in both Play and Prod. The portal has no `kb_` dependencies at all.

## ⚠⚠ A hand-edited `.srd` can fail even when every static check passes
**What happened:** the DataWindow binds columns by ordinal **position**, so removing 3 trailing
columns and appending 1 required editing the metadata list, header/detail visual objects, and a
stray footer `sum(extended_cost)` total in lockstep. `Build-BrWillCallOrders-Srd.ps1` did this
via text surgery on a copy of the source portal's `.srd`, and asserted positional order matched
the retrieve SQL before writing — **passed every check** (16/16/16 columns, correct order, no
leftover references, retrieve SQL round-tripped clean). It still crashed the P21 client on open:
`SelectElement`/`SelectPage` throwing before any query ran, no SQL error surfaced — the classic
"PowerBuilder couldn't build the DataWindow" trap (see `feedback_p21_portal_datawindow_sql_simple`).

**Isolated empirically, not by inspection:**
1. Swapped the one added JOIN (Carrier = Will Call) for a plain WHERE equality — identical
   crash. Ruled out SQL complexity.
2. Registered the byte-identical file under a brand-new, never-loaded DataWindow name
   (`br_will_call_orders_test2`, portal_element_uid 326) — identical crash. Ruled out a stale
   cached build on the P21 UI server.
3. That left the hand-spliced file structure itself as the only remaining variable — not
   findable by further text/regex inspection of a file whose exact binary-ish grammar isn't
   fully documented.

**Fix:** had the user rebuild the DataWindow in **InfoMaker** — the actual PowerBuilder
DataWindow painter — off the retrieve SQL directly, instead of continuing to hand-edit `.srd`
text. Opened and ran correctly immediately.

**Rule going forward:** hand-editing a `.srd`'s raw text is only safe for a **pure SQL-string
swap with the column set completely unchanged** (the pattern that worked for SA-48732 —
`csr_open_order_team`, same 19 columns before and after). The moment a column is added or
removed, rebuild in InfoMaker — do not trust static text-level verification alone, no matter
how many checks pass.

## Order Id drill-through — not an `.srd` property
Drill-through is configured in `dc_nav_drill`, a separate DB table, not the `.srd` file:
`source_window='w_portal'`, `source_datawindow='udp_' + datawindow_name`,
`source_field` = the DataWindow's column name for order_no (`p21_view_oe_hdr_order_no`, since
the SQL references `p21_view_oe_hdr.order_no` unaliased — PowerBuilder auto-names it that way).
Modeled on the sibling `CSR WILL ADVISE` portal's existing row (`udp_csr_will_advise`,
`dc_nav_drill_uid` 31). Registered for this portal via `Register-BrWillCallOrders-Drill-Play.sql`
→ `dc_nav_drill_uid` 152 (Play). **If the InfoMaker rebuild ever changes the generated column
name for order_no, this row's `source_field` needs to match it exactly** — verify before
promoting to Prod.
